# Phase 2 gate: the control plane runs without me

*2026-08-05 · ai-portfolio-sentinel · learning lane. Status: in
development toward production-ready. No production claim is made here.*

What changed at this gate is one specific thing: the pipeline now runs
end to end, and something other than my hands starts it. Two
consecutive runs were triggered by Windows Task Scheduler —
`r-91ec8071505a4ba7905fe6f9ef4c53f4` started 2026-08-05T09:01:39Z and
`r-5ac95d4bc6fd4c55a7f739547090098f` started 2026-08-05T09:21:40Z —
both landing COMPLETED in the ledger, 190 of 190 tasks terminal on
each, `LastTaskResult=0` on each. Nothing was invoked by hand between
them; the scheduled structured log, the ledger's run IDs and
timestamps, and the FINDINGS.md sections all correlate to the same two
events.

What was built is deterministic-first. Inventory is derived live from
the public GitHub API — no list to go stale. One task per surface ×
check class, and four of the six classes do real work: broken-link,
number-mismatch, missing-required-file, readme-structure. Live
applicability for the last two isn't a static rule — it's read, per
repository, per run, from that repository's own `.githooks/pre-push`
and gate-file content, never from this repo's own convention. The
other two classes — stale-STATE-marker, missing-synthetic-label — are
honest stubs until a caged agent lands at Phase 3; their tasks still
run and reach DONE, correctly finding nothing, rather than being
skipped. Dedup is a fingerprint over surface, class, and a
finding-local content hash, deliberately never a whole-file hash — an
unrelated edit elsewhere in a file must not resurrect or bury a
finding. The database refuses deletes at the schema level, not by
convention.

482 tests pass, 4 skip (the Phase 3/4 breaker stubs, and only those —
a self-checking test pins the set). Line coverage is 89.9% over the
pipeline. Every CostRow this phase, across three real runs, shows zero
tokens and zero cost — this phase makes no model calls at all, and a
telemetry harness that reports zero honestly is worth having before it
ever has to report something else.

The harder part wasn't the pipeline — it was the scheduler script,
because I only found out it was broken by actually running it. Windows
PowerShell 5.1 doesn't reliably read a script's non-ASCII characters
without a byte-order mark, so an em dash in a comment quietly broke
string parsing three lines later. Separately, `$PSScriptRoot` — the
variable a script uses to find its own folder — isn't populated yet
when a `param()` block's default values are evaluated on this
PowerShell version. Both are exactly the kind of thing that never
shows up in a design review and always shows up the first time
something runs for real. Fixed, and now covered by an actual execution
of the script, not just a unit test of the Python module that mirrors
its argument list.

Two labels, kept apart on purpose. The eval gate runs on synthetic
fixtures with a frozen answer key, unchanged since
`4d46c1d4fc3c4f485a83f44fa54afa6b04b1f541`. The three runs described
above are live: real data, my own public repositories, read-only, no
credentials held for any of them. The schedule fires while my machine
is on and I'm logged in — that's what "unattended" means here, and
it's the whole of what it means.
